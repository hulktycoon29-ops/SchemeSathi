1. Project Executive Summary

SchemeSathi solves the information fragmentation problem faced by Indian students attempting to discover and navigate government and private educational scholarship programs. Instead of parsing dense PDF eligibility guidelines, students submit their academic marks, annual family income, and demographic category. The system executes a polymorphic OOP rule engine to determine real-time qualification, outputs reasons for disqualification, lists mandatory documentation, and generates auditable text reports.

Dual Interface Architecture:
1. Headless Interactive Console (CLI): Pure Java console interface for terminals and low-resource environments.
2. Cloud REST API + Modern Web Application: Embedded HTTP microserver powering a responsive React web interface with light/dark themes and a dedicated administrative session auditing gateway.

2. Complete OOP Concepts Mapping

Every single core concept of Object-Oriented Programming has been deliberately implemented and cleanly decoupled in the codebase.

OOP Concept Where is it Implemented? How does it Work in SchemeSathi?
1. Abstraction • com.schemesathi.model.Scheme
• com.schemesathi.report.ReportWriter 		Scheme is an abstract class defining common attributes (id, name, required documents) and abstract methods isEligible(Student s) and getCriteriaDescription(). Callers don't need to know how rules work internally.
ReportWriter is an interface hiding file I/O operations behind a clean generateReport(...) signature.
2. Encapsulation • Student.java
• User.java
• AuthService.java 		All member fields are declared private. Access is regulated via validated getters and setters. In Student, marks must be 0–100% and income cannot be negative. In User, password hashes and salts are strictly immutable once created.
3. Inheritance • MeritScheme extends Scheme
• IncomeScheme extends Scheme
• CategoryScheme extends Scheme 		Subclasses inherit common attributes and behaviors from Scheme using super(id, name, type, docs), while introducing specialized rule fields (e.g. minimumMarks in MeritScheme, maximumAnnualIncome in IncomeScheme).
4. Polymorphism • EligibilityService.java
• Dynamic method dispatch in scheme.isEligible(student) 		The engine holds a polymorphic collection List<Scheme>. At runtime, when scheme.isEligible(student) is invoked, Java automatically executes the correct subclass logic (Merit vs. Income vs. Category) without any instanceof checks or switch statements.
Deep Dive into Polymorphism in Action:
In EligibilityService.java: 
public List<Scheme> findEligibleSchemes(Student student, List<Scheme> schemes) {
    List<Scheme> eligible = new ArrayList<>();
    for (Scheme scheme : schemes) {
        // POLYMORPHIC CALL: Dynamic dispatch binds to concrete subclass at runtime!
        if (scheme.isEligible(student)) {
            eligible.add(scheme);
        }
    }
    return eligible;
}
If a new scholarship type (e.g., SportsScheme) is added tomorrow, zero lines of code in EligibilityService need to change. This satisfies the Open/Closed Principle (SOLID).

3. Complete End-to-End Execution Flow

How a student profile travels from the user's browser, through network boundaries, into the OOP engine, and back:

  1. User Authentication & Gateway Check:
    The user enters credentials into the React frontend. The request hits /api/auth/login (or /api/auth/register). AuthService computes SHA-256(password + salt). If valid, an encrypted session token STOK-... is returned and stored in the browser's localStorage.
  2. Student Profile Ingestion:
    The user specifies their marks (e.g., 85.5%), family annual income (e.g., ₹2,40,000), and category (e.g., OBC).
  3. REST API Dispatch:
    The React client issues an asynchronous HTTP POST to /api/evaluate with a JSON payload.
  4. Object Instantiation (Encapsulation):
    The backend EvaluateHandler parses JSON and constructs an immutable Student domain object: Student student = new Student("S101", "Rahul", 85.5, 240000.0, "OBC");.
  5. Polymorphic Evaluation:
    EligibilityService.evaluateWithBreakdown(student, schemes) iterates through all loaded schemes. For each scheme:
    • MeritScheme.isEligible(): Checks if student.getMarksPercentage() >= minimumMarks.
    • IncomeScheme.isEligible(): Checks if student.getAnnualIncome() <= maximumAnnualIncome.
    • CategoryScheme.isEligible(): Checks if allowedCategories.contains(student.getCategory()).
  6. Report Generation (Interface Abstraction):
    EligibilityReportWriter generates a formatted audit report into output/eligibility-report.txt, detailing qualifying and non-qualifying schemes with reasons.
  7. Client Presentation:
    The HTTP server returns HTTP 200 with JSON breakdown. The React interface triggers an electric loading transition and reveals the qualified scholarships and document checklists.
Admin Auditing Flow:
Whenever any user signs in or checks schemes, AuthService.recordLoginAttempt(...) stores an immutable LoginRecord with IP address, role, and ISO timestamp. Only users authenticated with role ADMIN (e.g. Priyanshu) can access /#/admin, fetch live audit telemetry, or download the full audit log as a CSV spreadsheet.

4. High-Yield Viva & Defense Q&A

Use these structured answers during your presentation to impress your professors or evaluators:

Q1: Why did you make Scheme an abstract class instead of an interface?
Answer: An abstract class was chosen because all scholarships share common state (fields: id, name, type, requiredDocuments) and common behavior (getters, setters, document validation). An interface in Java cannot hold instance state. By using an abstract class with a super(...) constructor, we achieve code reusability while still enforcing abstract methods (isEligible) on every subclass.
Q2: Where is Dynamic Method Dispatch (Runtime Polymorphism) used?
Answer: In EligibilityService.java, line 20: scheme.isEligible(student). The variable scheme is declared as the abstract base type Scheme, but points to instances of MeritScheme, IncomeScheme, or CategoryScheme. Java resolves which method implementation to execute at runtime based on the actual object in memory.
Q3: How have you applied Encapsulation and Data Protection?
Answer: 1. In Student.java, all fields are private with input validation in constructors and setters (e.g. throwing IllegalArgumentException if marks are negative or exceed 100%).
2. In AuthService.java, passwords are never stored in plaintext. They are protected using SHA-256 cryptographic hashing combined with a 16-byte cryptographically secure random salt generated via SecureRandom.
Q4: How does the Java backend communicate with the React frontend?
Answer: We built an embedded HttpServer in ApiServer.java listening on a configurable port. It exposes RESTful JSON endpoints (/api/evaluate, /api/schemes, /api/auth/login) and includes CORS headers (Access-Control-Allow-Origin: *) to allow seamless cross-origin requests from the React client.
Q5: How is this project deployed in production?
Answer: We containerized the backend using a multi-stage Dockerfile with Maven build and an eclipse-temurin:17-jre minimal runtime. The backend is deployed as a Docker Web Service on Render Cloud reading dynamic $PORT variables. The React frontend is deployed as a high-performance Static Site with client-side rewrite rules.
Q6: How does the system handle unit testing?
Answer: We wrote 24 comprehensive JUnit 5 unit tests covering StudentTest, SchemeTest, EligibilityServiceTest, SchemeLoaderTest, EligibilityReportWriterTest, and AuthServiceTest. All tests run and pass automatically during mvn test.
